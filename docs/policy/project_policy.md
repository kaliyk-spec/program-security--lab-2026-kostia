Ця політика визначає обов'язкові вимоги до коду та архітектури Secure Vault Service — системи централізованого, криптографічно захищеного зберігання секретів. Ключові вимоги: строго типізоване ООП за SOLID, чистий код, шарова архітектура з примусовими межами між шарами.

Сервіс фокусується виключно на криптографічному захисті та керуванні життєвим циклом секретів; автентифікація користувачів та управління обліковими записами свідомо виносяться за межі сервісу в модуль `Identity`.

## Правила зміни політики
- **Жодних змін мимохідь** — політика змінюється лише окремою задачею.
- **Обов'язковий апрув** — будь-яка зміна попередньо погоджується з власником проекту.
- **Окремий комміт** — зміни йдуть коммітом з префіксом `[POLICY]`.

## 1. Скоуп
Ця політика поширюється на проект Secure Vault Service — на весь вихідний код (`src/`) та тести (`tests/`). Вона обов'язкова для всіх розробників та AI-агентів.

## 2. Технології
- **C# 12 / .NET 8**
- **Entity Framework Core** (Infrastructure / Persistence)
- **xUnit, FluentAssertions, Moq** (Тестування)
- **NetArchTest / ArchUnitNET** (Контроль меж шарів та правил архітектури)
- **Git**

## 3. Фундаментальні принципи
- **Розділення шарів.** Змішування інфраструктурного шару, бізнес-логіки та Presentation строго заборонене. Внутрішні шари ніколи не залежать від зовнішніх.
- **DDD для бізнес-логіки.** Бізнес-логіка реалізується виключно в межах Domain-Driven Design через сутності, агрегати, VO, доменні сервіси та політики.
- **Чужа логіка поза проектом.** Сервіс не валідує ідентичність користувачів (це зона `Identity`), а оперує готовими зовнішніми контекстами/ідентифікаторами.
- **Строго типізоване ООП, SOLID, чистий код.**
- **Криптографічна ізоляція.** Жодні відкриті секретні дані не зберігаються в персистентному стані сутностей.
- **Непорушність політики.** Жодні обставини не є легітимною підставою для порушення цієї політики.

## 4. Архітектура та структура

Виклики йдуть зверху вниз:

Структура `src/`:

```
src/
├── Presentation/             # Точка входу: Web API контролери, ендпоінти, middleware
│
├── Application/              # Шар оркестрації (CQRS)
│   └── Vault/
│       ├── Command/          # Application Commands (наміри мутації: StoreSecretAC)
│       ├── Query/            # Application Queries (наміри читання: GetSecretAQ)
│       ├── UseCase/          # Оркестратори (хендлери операцій)
│       ├── Dto/              # Вхідні/вихідні моделі даних (SecretMetadataDTO)
│       └── Exception/        # Винятки рівня застосунку
│
├── Domain/                   # Чиста бізнес-логіка (без зовнішніх бібліотек)
│   ├── SharedKernel/         # Базові доменні абстракції
│   │   ├── Abstracts/        # AEntity, AValueObject, ADomainEvent, AServiceException
│   │   ├── Contract/         # Інтерфейси фундаментальних елементів
│   │   └── ValueObject/      # Спільні ідентифікатори (AEntityIdVO)
│   │
│   └── Vault/                # Bounded Context сховища секретів
│       ├── Entity/           # SecretItem (Aggregate Root), AuditLog
│       ├── ValueObject/      # SecretNameVO, EncryptedDataVO, SecretStatusVO
│       ├── Policy/           # Доменні правила (AccessSecretDPolicy, RevokeSecretDPolicy)
│       ├── Service/          # Доменні сервіси (StoreSecretService, AccessSecretService)
│       ├── Event/            # Доменні події (SecretStoredDE, SecretRevokedDE)
│       ├── OutsourceContract/# Контракти до інфраструктури (ICryptoProvider, ISecretRepository)
│       └── Exception/        # Доменні винятки
│           ├── Abstracts/    # AVaultException
│           └── Registry/     # VaultExceptionRegistry (коди SVS.VAULT.X)
│
└── Infrastructure/           # Реалізація технічних деталей
    ├── Persistence/          # EF Core DbContext, міграції, репозиторії
    ├── Cryptography/         # Реалізація ICryptoProvider (AES-256-GCM тощо)
    └── Exception/            # Інфраструктурні помилки
        ├── Abstracts/        # AInfrastructureException
        └── Registry/         # InfrastructureExceptionRegistry (коди SVS.INF.X)
```

## 5. Політика доменних івентів
- Кожен Domain Event (`DE`) фіксує значущу подію в домені.
- Складається з: `Id` (GUID події), `AggregateId` (ідентифікатор секрету), `TimestampUtc`, типу події та типізованого пейлоада (DED).
- **Суворе правило безпеки:** Доменні події ніколи не містять відкритих або зашифрованих секретних пейлоадів (лише ідентифікатори, версії, таймстемпи та метадані дій).
- Події збираються всередині Aggregate Root і витягуються (`pullEvents`) інфраструктурою/хендлером після фіксації транзакції.

## 6. Політика неймінгу

| Елемент | Конвенція | Приклад |
|---|---|---|
| Інтерфейс | префікс `I` | `ISecretRepository`, `ICryptoProvider` |
| Абстрактний клас | префікс `A` | `AEntity`, `AValueObject` |
| Entity / Aggregate Root | PascalCase (без суфікса) | `SecretItem`, `AuditLog` |
| Value Object | суфікс `VO` | `SecretNameVO`, `EncryptedDataVO` |
| Доменний сервіс | суфікс `Service` | `StoreSecretService` |
| Доменна політика | суфікс `DPolicy` | `AccessSecretDPolicy` |
| Доменна подія | суфікс `DE` | `SecretStoredDE`, `SecretRevokedDE` |
| Use Case / Handler | суфікс `UC` / `Handler` | `StoreSecretUC` |
| Application Command | суфікс `AC` | `StoreSecretAC` |
| Application Query | суфікс `AQ` | `GetSecretAQ` |
| DTO | суфікс `DTO` | `SecretMetadataDTO` |
| Реєстр кодів винятків | суфікс `ExceptionRegistry` | `VaultExceptionRegistry` |
| Конкретний виняток | суфікс `Exception` | `SecretAlreadyRevokedException` |

## 7. Політика документації коду (XML Documentation)
Для кожного публічного методу, властивості, сутності та VO обов'язкові стандартні XML-коментарі (`///`):
- `<summary>`: пояснення бізнес-ролі та призначення.
- `<param>`: опис ролі параметрів.
- `<exception>`: список можливих доменних чи інфраструктурних винятків.
- Для `Entity` та `ValueObject` у коментарі класу обов'язково перераховуються **Invariants**.

## 8. Політика винятків
- Усі винятки проекту походять від єдиного базового винятку `AVaultServiceException` (з кодом та сегментом).
- **Формат коду:** `SVS.<Сегмент>.<Код>` (наприклад: `SVS.VAULT.1`, `SVS.INF.3`).
    - `SVS` — Secure Vault Service префікс.
    - `VAULT` — сегмент бізнес-контексту.
    - `INF` — інфраструктурний сегмент.
    - `CORE` — SharedKernel.
- Коди закріплені в типізованих реєстрах (Enum) і є іммутабельними. Видалені коди маркуються атрибутом `[Obsolete]`.
- Системні чи сторонні бібліотечні помилки перехоплюються в Infrastructure/Application та обгортаються у внутрішні винятки.

## 9. Політика Null-Safety
- У проекті увімкнено C# `<Nullable>enable</Nullable>`.
- Використання чистого `null` для позначення бізнес-станів мінімізується на користь Null-Object / Result-патернів або типізованих обгорток. Поля сутностей не повинні містити непроініціалізований `null`.

## 10. Політика тестування
- **xUnit** — основний фреймворк тестування. Жодних реальних запитів до зовнішніх систем чи реальної криптографії ОС у юніт-тестах (використовуються інвертовані інтерфейси й Test Doubles).
- **Domain:** виключно чисті Unit-тести на інваріанти, правила створення, політики та зміну статусів (100% критичних шляхів).
- **Application:** Unit-тести валідації команд/запитів та оркестрації юзкейсу.
- **Infrastructure:** інтеграційні тести EF Core (InMemory / TestContainers) та перевірка контрактів криптопровайдерів.
- Тести обов'язково покривають як Happy Path, так і сценарії порушення інваріантів з перевіркою викинутого типізованого винятку.

## 11. Git Workflow
- Гілки: `main` (продакшн), `develop` (робоча гілка), `feat/DEV-XXX-назва`, `fix/FIX-XXX-назва`.
- Зміни політики: обов'язковий окремий комміт з тегом `[POLICY]`.
- Формат коммітів: `[DEV-123] Додано сутність SecretItem`.

## 12. Політика документації розробки
- Документація зберігається поруч із кодом у папці `docs/`.
- Файл `business_logic.md` у кожному контексті є єдиним джерелом правди про призначення, сутності, VO, матриці статусів та інваріанти. Зміна логіки в коді без оновлення специфікації вважається дефектом.

## 13. Анти-патерни
1. **Зберігання відкритого секрету в агрегаті:** наявність полів з відкритим текстом у `SecretItem`.
2. **Протікання інфраструктури в Domain:** пряме підключення сторонніх Nuget-пакетів криптопровайдерів або EF Core у Domain-проект (лише через `OutsourceContract`).
3. **Витік секретів через Domain Events:** додавання зашифрованого/дешифрованого вмісту у пейлоад івента.
4. **Товстий Use Case:** розміщення валідації переходів між статусами в Application-шарі замість методів сутності та Domain Policies.
5. **Розмиті винятки:** викидання `Exception` або `InvalidOperationException` замість типізованих класів доменних винятків із кодом.
